# Genblaze feedback draft: ObjectStorageSink fails with B2 after successful provider output

## Summary

`ObjectStorageSink` receives HTTP 401 while uploading a successfully generated local-file image asset to a Backblaze B2 bucket. Direct `S3StorageBackend.for_backblaze(...).put(...)` with the same credentials and bucket succeeds.

## Environment

- Genblaze / `genblaze-s3` / `genblaze-gmicloud` from the current installed release
- Backblaze B2 S3-compatible bucket with Object Lock enabled
- Account-level application key with list/read/write plus retention capabilities
- Custom `SyncProvider` returns a valid `file:///.../output.png` asset after a Google Gemini image response

## Expected

`Pipeline(...).run(sink=ObjectStorageSink(S3StorageBackend.for_backblaze(...)))` uploads the generated local-file asset and manifest to B2.

## Actual

The generation succeeds, then the sink fails with an HTTP 401 during transfer to a B2 key shaped like:

```text
https://s3.<region>.backblazeb2.com/<bucket>/recall/genblaze/runs/<date>/<run>/assets/<asset>.png
```

The same credentials can immediately upload asset bytes with the direct `S3StorageBackend` wrapper. No credentials, bucket names, or signed URLs should be included in the public issue.

## Impact

Apps can retain the complete Genblaze manifest and generated bytes with direct B2 writes, but cannot use the native sink path for this provider/output combination. A fix would make B2-first provenance pipelines simpler and more reliable.
